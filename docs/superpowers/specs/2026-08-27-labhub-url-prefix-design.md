# LabHub Production URL Prefix Design

## Goal

Ensure every URL generated by Django in production uses the public base URL
`https://lab1.trisakti.ac.id/labhub/`, while local development can continue to
run at `/` without a deployment-specific URL prefix.

## Configuration

Production supplies these environment values:

```text
FORCE_SCRIPT_NAME=/labhub
PUBLIC_ACCESS_BASE_URL=https://lab1.trisakti.ac.id/labhub
```

`FORCE_SCRIPT_NAME` remains the single source of truth for Django-generated
paths. `PUBLIC_ACCESS_BASE_URL` is used only when the application must create an
absolute public URL, such as a link sent in a notification or email.

The reverse proxy keeps the public `/labhub/` prefix for HTTP requests. For
WebSockets, Apache maps public `/labhub/ws/` to backend `/ws/` because Channels
routes WebSocket paths independently of Django's script prefix.

## Application Changes

Audit templates and browser-side code for root-relative hard-coded URLs such as
`href="/"`, `fetch("/...")`, and `/ws/...`. Replace them with Django-generated
URLs or a script-prefix value rendered by Django. Do not add `labhub` directly
to `urlpatterns`, because doing so would duplicate the prefix in production and
make local development unnecessarily deployment-specific.

Cookie paths should follow the script prefix in production so authentication
and CSRF cookies remain scoped to the application without affecting other apps
on `lab1.trisakti.ac.id`.

## Verification

Automated deployment tests cover reverse URL generation and redirects with a
`/labhub/` script prefix. Focused tests cover login, dashboard, health, static,
media, API, and WebSocket URL construction. A final public smoke test verifies
that `/labhub/` redirects to a prefixed login URL and that no response redirects
to an unprefixed application path.

## Scope

This change only normalizes application URLs. It does not move the application,
change database data, alter authentication rules, or redirect the domain root
`https://lab1.trisakti.ac.id/`.
